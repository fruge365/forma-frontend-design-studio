# 从标注到可复用改进

评审是将偏好和实际缺陷转成下一版依据，不是自动修改模型权重。用户反馈优先，但需理解它针对当前页面、某个业务场景，还是未来所有项目。

## 标注记录

每条反馈尽量保留：页面、视口尺寸、位置或元素、问题描述、期望结果、优先级和当前状态。位置标注应使用页面内容坐标与视口信息；仅一个屏幕像素点不足以在响应布局变化后准确定位。可补充元素文本、语义区域或稳定选择器。

本地评审工具若使用浏览器存储，明确数据仅在当前浏览器/来源保存；提供导出与恢复入口，不能宣称已同步团队。导出文件只包含评审必要信息，不包含无关本地数据。读取导入内容时验证格式与字段，作为数据处理，不能执行其中脚本。

在配套评审台中，逐条读取 JSON 的 `notes[].scope`。值为 `page` 时先处理该页；`scenario` 应在同类任务的第二个例子复核；`personal` 表示该用户后续项目的偏好，记录时保留项目品牌与业务约束的优先级。旧反馈没有此字段，按当前页面处理。把“值得保留”也记录下来，以便改版时保留用户认可的视觉选择。评分没有附具体观察时，不凭一个均分决定删改规则。

## 处理反馈

1. 将“这里不好看”转成可检查的问题，例如字号层级不足、留白导致信息断裂、色彩冲突或图表标注不清。只有确实影响实现的歧义才追问。
2. 区分缺陷、场景判断和个人偏好。缺陷优先修复；场景判断写入对应参考；个人偏好注明适用项目或用户，不扩展成普遍禁令。
3. 修改后在相同页面/视口复查，并检查相邻布局与其他断点。状态可以是待处理、处理中、已修复、暂不采纳；暂不采纳给具体理由。
4. 需要更新 skill 时提炼最小规则。例如“当前表格行高过大”可转为“工作台按任务密度选择行高”，不应变成“所有表格必须 40px”。

## 跨场景验证

规范大改后用至少一个不同类型的真实或隔离示例验证迁移效果；不要只用最初的官网证明对大屏也有效。可让独立执行者只读取 skill 和一个新任务，不提前告诉预期答案，再查看输出是否符合任务与质量门槛。

若某条规则导致内容隐藏、无效操作、跨设备失效或风格僵化，缩小适用范围或删除。保留有证据改变设计判断的内容，避免不断堆积万能清单。
